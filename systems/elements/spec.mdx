# 원소 기능정의

## 1. 기능 범위

현재 기능정의의 기준 범위는 **원소 조회, 원소 조합, AI 신규 원소 생성, 결과 저장**입니다. 영업 시작 전 원소 사전 보관 기능은 2026-08-24 결정으로 Deprecated 처리합니다.

## 3. 핵심 처리 규칙

### 조합 요청

입력: `user_id`, `element_a_id`, `element_b_id`, 요청 컨텍스트

처리:

1. 두 원소의 보유/사용 가능 상태를 검증합니다.
2. 두 ID를 정렬해 `combination_key`를 생성합니다.
3. `ElementRecipeData`를 먼저 조회합니다.
4. 결과가 있으면 AI 호출 없이 기존 결과를 반환합니다.
5. 없으면 AI 신규 생성 프로세스로 이동합니다.

출력: 결과 원소 ID, 신규 여부, 이름, 설명, 색상

### AI 신규 생성

입력은 두 원소의 이름/설명/색상, `ElementTagAffinity`, 활성 태그 목록과 판정 가이드, 세계관 톤입니다.

필수 출력은 `name`, `description`, `color_hex`, `tag_affinities`입니다. `tag_affinities`는 최대 4개이며 각 값은 `1~5`이고 활성 태그 ID만 사용할 수 있습니다. 입력 원소의 Affinity를 단순 합산/평균하지 않고 AI가 생성한 신규 원소의 실제 물성·현상 설명을 기준으로 다시 선정합니다.

검증 실패 시 재생성할 수 있으나 재시도 횟수와 최종 실패 처리는 TBD입니다.

## 4. 데이터 계약

### ElementData

`element_id`, `element_name`, `description`, `primary_color_hex`, `secondary_color_hex`, `accent_color_hex`, `source_type`, `is_ai_generated`, `status`, 생성/수정 시각과 원소의 `ElementTagAffinity`를 가집니다.

`ElementTagAffinity`는 `element_id`, `tag_id`, `affinity(1~5)` 개념으로 관리하며 원소당 최대 4개입니다. 기본/운영 원소는 사람이 지정하고 AI 조합 원소는 최초 생성 시 AI가 지정한 뒤 저장합니다. 운영자는 저장된 Affinity를 수정할 수 있습니다.

### ElementRecipeData

`recipe_id`, `combination_key`, `element_a_id`, `element_b_id`, `result_element_id`, `generation_type`, `status`를 가집니다.

### UserElementData

유저 보유 원소와 획득 방식을 관리합니다.

### Deprecated: UserElementStorageData

당일 보관 원소 목록을 저장하던 과거 구조입니다. 신규 구현 기준에서 사용하지 않습니다. 기존 데이터 마이그레이션/삭제 여부는 개발 정책으로 별도 결정해야 합니다.

## 6. 예외

- 미보유/비활성 원소: 요청 거부
- 기존 조합: AI 호출 없이 캐시 결과 반환
- AI 응답 실패: 재시도 정책 적용
- 잘못된 HEX/필수값 누락: 검증 실패
- 등록되지 않았거나 비활성인 태그 ID: 검증 실패
- Affinity 값 범위 이탈, 4개 초과, 중복 태그: 검증 실패
- 중복 이름: 기존 데이터와 충돌 처리

## 7. 미확정 정책

- 동일 원소 조합 허용 여부
- 조합 비용
- 생성 일일 제한
- 중복 획득 처리
- AI 최종 실패 처리
