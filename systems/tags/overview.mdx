# 태그 시스템

## 1. 개요

태그 시스템은 NPC 의뢰가 요구하는 무기의 성질, 완성 무기가 실제로 가진 성질, 원소가 만들어내기 쉬운 성질을 하나의 공통 어휘로 연결하는 핵심 평가 시스템입니다.

태그는 사람이 관리하는 고정 사전이며 AI가 새로운 태그를 임의로 만들 수 없습니다. 플레이어는 NPC의 대화와 원소의 공개 성향을 해석해 원하는 태그 조합에 가까운 무기를 제작하고, 완성 무기는 AI 판정을 거쳐 평가용 태그를 확정합니다.

### 1.1 기획 의도

- NPC의 자연어 요구를 제작 결과와 비교 가능한 내부 데이터로 연결합니다.
- 같은 계열의 원소 중 어떤 원소를 선택할지 고민하게 만듭니다.
- 제작 결과가 요구보다 부족하거나 과한 경우 모두 의미 있는 차이로 평가합니다.
- AI의 자유로운 용어 생성을 제한하고 사람이 통제 가능한 데이터 사전을 유지합니다.
- 향후 태그 관계도, 요청 티어, 무기 티어 등 고도화가 가능한 기반을 확보합니다.

### 1.2 목표

- 의뢰와 무기는 동일한 `TagDefinition`을 참조합니다.
- 태그 강도는 `0~5` 범위로 표현합니다.
- 완성 무기의 대표 태그는 AI Raw 판정과 코드 기반 선정 정책으로 결정합니다.
- 원소는 무기 태그를 직접 보유하는 대신 `ElementTagAffinity`로 발현 경향을 가집니다.
- MVP 평가는 요구 태그와 실제 무기 태그의 값 차이를 기본 거리로 사용합니다.

### 1.3 범위

**MVP 포함**

- 사람이 관리하는 태그 사전
- 의뢰 요구 태그
- 완성 무기 Raw 태그 판정과 대표 태그 선정
- 원소 태그 친화도
- 기본 거리 기반 의뢰-무기 비교
- 태그 활성/비활성 운영 정책

**MVP 이후 고도화**

- 태그 간 유사/반대 관계도
- 태그별 중요도 가중치
- 무기 파츠 단위 태그
- 요청 티어에 따른 요구 태그 수/복잡도
- 무기 티어에 따른 대표 태그 수 확장
- 관계도를 이용한 모순 검증 및 부분 점수

## 2. 용어 정의

| 용어 | 정의 |
| --- | --- |
| `TagDefinition` | 사람이 정의하고 관리하는 태그 사전 항목 |
| 태그 값 | 해당 성질이 얼마나 강하게 존재하는지 나타내는 `0~5` 값 |
| 요구 태그 | NPC 의뢰에 기획자가 직접 지정한 목표 태그와 목표 값 |
| Raw 태그 판정 | AI가 활성 태그 전체에 대해 반환한 원본 평가 결과 |
| 무기 태그 | Raw 판정에서 선정 정책을 통과해 실제 평가에 사용하는 대표 태그 |
| `prominence` | 해당 성질이 무기를 대표하는 정도. 대표 태그 선정에 사용 |
| `confidence` | AI 판정 확신도. 디버깅용이며 게임 점수에는 사용하지 않음 |
| `ElementTagAffinity` | 원소가 특정 무기 태그를 발현시키기 쉬운 정도 |
| `TagRelation` | 태그 간 유사/반대 관계. MVP 이후 사람이 관리하는 관계 데이터 |

## 3. 시스템 구조

```text
                    TagDefinition
                         │
          ┌──────────────┼──────────────┐
          │              │              │
          ▼              ▼              ▼
      요구 태그     ElementTagAffinity   무기 Raw 판정
  (기획자 직접 입력)   (발현 경향)       (AI 평가)
          │              │              │
          │              └──── 제작 ────┤
          │                             ▼
          │                      대표 WeaponTag 선정
          │                             │
          └────────────── 비교 ─────────┘
                         │
                         ▼
                    평가 입력값
```

태그 시스템은 원소의 Affinity를 완성 무기 태그로 복사하지 않습니다. 원소는 제작 방향을 만드는 입력이며, 무기 태그는 완성 결과를 다시 판정한 결과입니다.

## 4. 핵심 규칙

### 4.1 태그 사전 관리

- 태그 목록은 사람이 정의하고 운영합니다.
- AI는 제공된 활성 태그 목록 중에서만 선택하거나 값을 평가할 수 있습니다.
- 내부 `tag_id`와 플레이어/기획자에게 보이는 `display_name`을 분리합니다.
- 한 번 사용된 `tag_id`는 표시명이 바뀌어도 유지합니다.
- 태그 삭제보다 `is_enabled = false` 비활성화를 사용합니다.
- 비활성 태그는 신규 AI 판정과 신규 원소 생성에서 제외하되 기존 데이터의 참조는 유지합니다.

### 4.2 명칭 규칙

태그는 무기를 자연스럽게 수식할 수 있는 표현으로 작성합니다.

허용 예시:

- `날카로운`
- `무거운`
- `화려한`
- `불타는`
- `빛나는`

문법적으로 순수 형용사만 강제하지 않고 `불타는`, `빛나는`처럼 무기를 자연스럽게 수식하는 관형 표현을 허용합니다.

색상 자체는 태그로 관리하지 않습니다. `붉은`, `푸른`, `검은` 등은 별도 시각 데이터의 책임입니다.

동의어나 거의 같은 의미의 태그를 중복 등록하지 않습니다. 하나의 의미 축에는 가능한 한 대표 태그 하나만 둡니다.

### 4.3 관리 카테고리

카테고리는 검색, 운영, AI 프롬프트 구성용 메타데이터이며 MVP 점수 계산에는 관여하지 않습니다.

- 형태·비례
- 외형·표면
- 물성
- 인상·양식
- 원소·상태
- 제작·완성도
- 마법적 성질

`빠른`, `강력한`, `공격적인`처럼 실제 근거 없이 사용 결과를 추정해야 하는 지나치게 추상적인 기능 태그는 MVP 사전에서 제외합니다.

`성스러운`, `사악한`, `저주받은`, `불길한` 같은 세계관/마법 태그는 허용하되 실제 원소, 재료, 설정, 현상 등 근거가 있을 때만 높은 값을 부여합니다. 외형이 어둡거나 장식이 기괴하다는 이유만으로 `사악한` 또는 `저주받은`을 부여하지 않습니다.

### 4.4 태그 값

요구 태그와 무기 태그의 강도는 `0~5` 범위입니다.

| 값 | 의미 |
| --: | --- |
| 0 | 해당 특성이 없음 |
| 1 | 매우 약하게 드러남 |
| 2 | 약하게 드러남 |
| 3 | 명확하게 드러남 |
| 4 | 강하게 드러남 |
| 5 | 해당 대상의 대표 특성일 정도로 매우 강함 |

각 `TagDefinition`에는 공통 숫자 정의와 별도로 AI 판정용 `EvaluationGuide`를 둡니다. 가이드는 최소 `0 / 1 / 3 / 5` 기준점을 설명하고 `2 / 4`는 사이값으로 판정합니다.

`긴`, `무거운`, `넓은` 등 상대적인 태그는 전체 무기를 하나의 절대 척도로 비교하지 않고 **현재 WeaponType 내부의 일반적인 무기와 비교**해 판단합니다.

### 4.5 요구 태그

- NPC 의뢰의 정답 태그는 AI가 생성하지 않고 기획자가 직접 지정합니다.
- 플레이어는 내부 정답값보다 NPC 대사를 통해 요구 성질을 추론하는 것을 기본 경험으로 합니다.
- 요구 태그도 `0~5` 목표 값을 가집니다.
- 요구보다 부족한 경우와 과한 경우 모두 목표에서 벗어난 것으로 처리합니다.
- 요청 티어에 따른 요구 태그 최대 개수와 복잡도는 요청 시스템에서 별도로 정의합니다.
- 태그별 중요도 Weight는 MVP 이후 고도화합니다.

### 4.6 완성 무기 태그 판정

무기 태그는 완성 무기 전체를 대상으로 판정합니다. 파츠별 태그는 MVP 범위에 포함하지 않습니다.

AI 판정 입력은 다음 정보를 조합합니다.

- 완성 무기 결과의 시각 정보
- WeaponType
- 사용 원소와 원소 성향
- 재료 정보가 존재하는 경우 해당 메타데이터
- 길이, 폭, 무게 등 정제된 제작 결과 데이터
- 기타 태그 판정에 필요한 구조화된 결과 정보
- 활성 `TagDefinition`과 각 `EvaluationGuide`

제작 과정의 원시 로그를 그대로 전달하지 않고 최종 결과를 설명하는 정보로 정제해 제공합니다.

AI는 활성 태그 전체에 대해 다음 Raw 값을 반환합니다.

```json
{
  "tagId": "sharp",
  "value": 4,
  "prominence": 5,
  "confidence": 0.86
}
```

- `value`: `0~5`, 성질의 실제 강도
- `prominence`: `0~5`, 무기를 대표하는 정도
- `confidence`: `0~1`, 개발/디버깅용 확신도

`confidence`는 게임 평가 점수에 사용하지 않습니다.

대표 무기 태그 선정의 MVP 기본 정책은 다음과 같습니다.

1. `value == 0` 제거
2. `value` 내림차순 정렬
3. 같은 `value`에서는 `prominence` 내림차순 정렬
4. 설정된 최대 태그 종류 수만큼 선택

최대 태그 종류 수는 하드코딩하지 않고 설정값으로 관리합니다. 향후 무기 티어에 따라 확장할 수 있으며 정확한 MVP 수치는 확정 필요 항목으로 유지합니다.

대표 태그에서 제외된 Raw 태그는 실제 의뢰 평가에서 `0`으로 취급합니다. Raw 결과는 디버깅과 향후 선정 정책 재계산을 위해 보관합니다.

### 4.7 원소 태그 친화도

원소는 `WeaponTag`와 다른 의미로 동일한 `TagDefinition`을 참조합니다.

```text
WeaponTag
= 완성 무기가 실제로 가진 특성

ElementTagAffinity
= 해당 원소가 그 특성을 만들어내기 쉬운 경향
```

원소당 Affinity는 최대 **4개**이며 값은 `1~5`입니다. `1`도 허용합니다.

기본 원소 및 운영자가 등록한 원소는 기획자가 Affinity를 직접 설정합니다. AI 조합으로 처음 생성되는 원소는 AI가 활성 태그 목록에서 최대 4개를 선택하고 값을 생성합니다. 생성된 값은 원소 데이터와 함께 영구 저장되며 이후 운영자가 수정할 수 있습니다.

플레이어 UI에는 정확한 내부 숫자보다 다음 강약 구간을 기본 표시합니다.

| 내부 값 | UI 표시 |
| --: | --- |
| 1~2 | 약함 |
| 3 | 보통 |
| 4~5 | 강함 |

이를 통해 같은 계열 원소라도 서로 다른 성향 프로필을 만들 수 있습니다.

```text
불꽃
- 뜨거운: 강함
- 불타는: 강함
- 빛나는: 보통

화염강
- 단단한: 강함
- 뜨거운: 강함
- 견고한: 강함
- 빛나는: 약함
```

원소 자체의 투입 강도/수량 단계는 현재 두지 않습니다. 같은 불 계열에서도 여러 원소를 제공하고 Affinity 구성을 달리해 선택의 차이를 만듭니다.

### 4.8 AI 조합 원소와 태그

기존 원소 조합이 DB에 없으면 원소 시스템의 기존 정책대로 AI가 신규 원소를 생성합니다. 이때 이름, 설명, 색상과 함께 `ElementTagAffinity`도 생성합니다.

입력 원소의 Affinity를 단순 합산하거나 평균 내서 결과 Affinity를 만들지 않습니다. AI가 먼저 조합 결과 원소의 실제 물성/현상을 정의하고 그 결과에 맞는 태그를 선택합니다.

예를 들어 `불꽃 + 강철 → 화염강` 결과가 높은 열을 품지만 실제 화염은 내지 않는 금속이라면 `뜨거운`, `단단한`, `견고한`은 높고 `불타는`은 제외될 수 있습니다.

최초 생성된 결과 원소와 Affinity는 조합식과 함께 저장됩니다. 이후 동일한 순서 비의존 조합은 기존 저장 결과를 재사용하므로 플레이어 간 공략과 결과 일관성을 유지합니다.

MVP에서는 별도의 `ElementTrait` 체계를 두지 않습니다. 원소 조합 전용 성질 체계가 필요해질 경우 후속 고도화로 분리합니다.

## 5. 의뢰-무기 평가 규칙

MVP의 기본 평가는 요구 태그와 **선정된 WeaponTag**의 값 차이를 기준으로 합니다.

모든 관련 태그 ID의 합집합에 대해 다음 오차를 계산하는 구조를 출발점으로 사용합니다.

```text
태그 오차 = Σ |요구 값 - 무기 값|
```

예시:

```text
요구
날카로운 3
가벼운   2
화려한   1

무기
날카로운 2
가벼운   4
화려한   1
위압적인 2

오차
|3 - 2| = 1
|2 - 4| = 2
|1 - 1| = 0
|0 - 2| = 2
총 오차 = 5
```

요청하지 않은 무기 태그는 요구값 `0`으로 간주하므로 자연스럽게 감점됩니다. 부족, 초과, 불필요 태그를 별도 예외 공식으로 나누지 않고 목표값과 실제값의 거리로 통일합니다.

최종 평가 점수의 `0~100` 정규화 공식은 아직 확정하지 않습니다.

## 6. 사용자 흐름

```text
기획자가 NPC 요구 태그 정의
→ 플레이어가 NPC 대화에서 요구 성질 추론
→ 원소의 공개 성향을 비교해 제작 원소 선택
→ 무기 제작
→ 완성 무기 태그 Raw AI 판정
→ 코드에서 대표 WeaponTag 선정
→ 요구 태그와 WeaponTag 거리 계산
→ 평가 시스템에 결과 전달
→ 보상/후일담 처리
```

## 7. 상태와 운영 정책

### TagDefinition

```text
Enabled
→ 신규 요청/AI 판정/원소 생성에서 사용 가능

Disabled
→ 신규 사용 금지
→ 기존 저장 데이터 참조는 유지
```

태그 표시명 변경은 허용하지만 저장 ID는 유지합니다. 기존 태그를 다른 태그로 대체해야 할 경우 운영 마이그레이션으로 처리합니다.

### AI 생성 결과

잘못된 태그 ID, 값 범위 초과, 원소 Affinity 4개 초과, 중복 태그가 포함된 응답은 서버 검증에 실패합니다. 재생성/실패 처리의 횟수와 정책은 각 기능정의서에서 관리합니다.

## 8. 다른 시스템과의 연동

| 시스템 | 태그 시스템과의 관계 |
| --- | --- |
| 의뢰/내러티브 | 기획자가 정의한 요구 태그를 전달하고 플레이어에게 자연어 힌트를 제공 |
| 원소 | 원소별 `ElementTagAffinity` 저장, 조합 신규 원소 생성 시 Affinity 생성 |
| 무기 제작 | 완성 무기와 정제 제작 데이터를 태그 판정 입력으로 제공 |
| 무기 | WeaponType 기준 상대 판정 컨텍스트 제공, 최종 WeaponTag 보유 |
| 평가 | 태그 거리/오차를 점수 계산의 핵심 입력으로 사용 |
| 후일담/보상 | 최종 평가 결과를 분기와 보상 입력으로 사용 가능 |

향후 관계도는 다음 개념으로 확장합니다.


`TagRelation.strength`는 AI가 생성하지 않고 사람이 관리합니다.

## 10. 예외 및 실패 정책

- AI가 사전에 없는 태그를 반환하면 해당 응답을 유효한 결과로 확정하지 않습니다.
- 값 범위를 벗어난 태그는 검증 실패 처리합니다.
- 하나의 대상에 동일 `tag_id`가 중복 반환되면 검증 실패 또는 정규화 대상입니다.
- 원소 Affinity가 4개를 초과하면 검증 실패 처리합니다.
- `confidence`가 낮아도 MVP 게임 규칙상 자동 감점하지 않습니다. 개발 분석 데이터로만 사용합니다.
- 비활성 태그는 신규 생성에 사용하지 않지만 기존 저장 데이터는 삭제하지 않습니다.

## 11. MVP 제외 및 고도화 계획

### 태그 관계도

사람이 `-5~5` 관계 강도를 관리합니다.

```text
-5 = 완전한 반대
 0 = 관계 없음
+5 = 사실상 같은 방향
```

예:

```text
무거운 ↔ 가벼운   -5
뜨거운 ↔ 차가운   -5
우아한 ↔ 정교한   +3
```

고도화 이후에는 반대 태그 추가 감점, 유사 태그 부분 점수, AI 생성 결과 모순 검증 등에 사용할 수 있습니다.

### 기타

- 태그별 중요도 Weight
- 무기 파츠별 태그
- 무기 티어별 최대 태그 수
- 요청 티어별 요구 태그 개수/복잡도
- 태그 관계를 이용한 원소 조합 해석
- 별도 `ElementTrait` 체계

## 12. 확정 필요 항목

- 무기 대표 태그 최대 종류 수의 MVP 정확한 값
- 태그 오차를 최종 `0~100` 평가 점수로 정규화하는 공식
- 요청 티어별 요구 태그 수와 난이도 규칙
- AI 태그 판정 응답 검증 실패 시 재시도/최종 실패 정책
- 초기 태그 사전 후보의 최종 채택/삭제
