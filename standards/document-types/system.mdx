# 시스템 기획서 작성 가이드

`doc_type: system`

시스템 기획서는 **하나의 게임 시스템이 왜 존재하고 어떤 규칙으로 작동하는지**를 정의합니다. 구현 방법보다 게임 규칙·정책·상호작용을 우선합니다.

## 목차별 작성 가이드

| 목차 | 무엇을 작성하는가 | 간단한 예시 |
| --- | --- | --- |
| 1. 개요 | 시스템의 역할과 기획 의도를 설명합니다. | `태그는 의뢰와 무기의 내부 의미를 비교하기 위한 공통 속성 체계다.` |
| 1.1 기획 의도 | 왜 이 시스템이 필요한지, 어떤 재미/문제를 해결하는지 적습니다. | `NPC 대사 해석을 제작 결과 평가와 연결한다.` |
| 1.2 목표 | 시스템이 달성해야 하는 상태를 정의합니다. | `유사한 의미의 태그일수록 높은 평가 점수를 만든다.` |
| 1.3 범위 | 포함/제외 기능을 분리합니다. | 포함: `태그 생성·중복·평가`; 제외: `태그 관계 그래프 고도화` |
| 2. 용어 정의 | 시스템에서 쓰는 핵심 용어를 일관되게 정의합니다. | `요구 태그`, `무기 태그`, `중복도` |
| 3. 시스템 구조 | 주요 구성요소와 데이터 흐름을 개념적으로 설명합니다. | `NPC 대사 → 요구 태그 → 무기 태그 → 비교 → 평가` |
| 4. 핵심 규칙 | 플레이 결과에 영향을 주는 규칙을 명시합니다. | `태그 명칭은 형용사로 제한한다.` |
| 5. 사용자 흐름 | 플레이어 행동 기준으로 시스템이 언제 작동하는지 적습니다. | `의뢰 수락 → 제작 → 무기 전달 → 태그 비교` |
| 6. 상태와 전이 | 상태가 존재한다면 상태값과 전이 조건을 정의합니다. | `Draft → Generated → Evaluated` |
| 7. 다른 시스템과의 연동 | 입력·출력·의존 관계를 적습니다. | `NPC 시스템에서 요구 태그 수신`, `평가 시스템으로 점수 제공` |
| 8. 데이터 개념 모델 | 구현 스키마가 아니라 필요한 데이터 개념을 정의합니다. | `tag_id`, `name`, `count`가 필요하다.` |
| 9. 예외 및 실패 정책 | 잘못된 입력이나 생성 실패 시 게임 규칙 관점의 대응을 적습니다. | `AI 태그 생성 실패 시 제작 결과 확정 금지 또는 fallback 적용 TBD` |
| 10. MVP 제외 범위 | 후속 고도화 요소를 명시합니다. | `태그 간 연관 그래프`, `동의어 자동 병합 고도화` |
| 11. 확정 필요 항목 | 아직 선택하지 않은 정책이나 수치를 적습니다. | `중복 태그 가중 함수 TBD` |
| 변경 이력 | 규칙, 범위, 시스템 연동 변경을 기록합니다. | `v0.2.0: 태그를 MVP 평가에 포함` |

## 최소 Markdown 골격

```md
# 시스템명

## 1. 개요
### 1.1 기획 의도
### 1.2 목표
### 1.3 범위
## 2. 용어 정의
## 3. 시스템 구조
## 4. 핵심 규칙
## 5. 사용자 흐름
## 6. 상태와 전이
## 7. 다른 시스템과의 연동
## 8. 데이터 개념 모델
## 9. 예외 및 실패 정책
## 10. MVP 제외 범위
## 11. 확정 필요 항목
## 변경 이력
```

## 시스템 기획서에 넣지 않는 내용

- 특정 함수 이름이나 클래스 설계
- HTTP API 세부 스펙
- 담당자별 일정
- 대량 콘텐츠 행 목록

이 내용은 기능정의서, WBS, 콘텐츠/Data 문서로 분리합니다.
