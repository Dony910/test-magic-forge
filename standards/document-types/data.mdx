# Data 문서 작성 가이드

`doc_type: data`

Data 문서는 **시스템이나 콘텐츠에서 사용하는 실제 데이터 구조와 값의 기준**을 정의합니다. 시스템 기획서가 규칙과 의미를 설명한다면 Data 문서는 필드, 허용값, 제약, 데이터 목록과 관리 기준을 다룹니다.

## 언제 사용하는가

- 콘텐츠 데이터가 많아 시스템/콘텐츠 기획서에서 분리해야 할 때
- DB/CSV/Sheet의 열 의미와 제약을 문서화할 때
- enum, ID, 파라미터, 마스터 데이터의 기준을 공유할 때

## 목차별 작성 가이드

| 목차 | 무엇을 작성하는가 | 간단한 예시 |
| --- | --- | --- |
| 1. 데이터 목적 | 어떤 시스템이 이 데이터를 왜 사용하는지 적습니다. | `ElementData는 제작과 원소 조합에서 참조하는 원소 마스터 데이터다.` |
| 2. 데이터 소유권 | 어떤 시스템/팀이 기준 데이터를 관리하는지 적습니다. | `원소 시스템 소유, 기획 검토 후 서버 마스터 반영` |
| 3. 스키마 | 필드명, 타입, 필수 여부, 제약과 의미를 적습니다. | `element_id / UUID / required / unique` |
| 4. 허용값 및 Enum | 제한된 값과 각각의 의미를 정의합니다. | `source_type: base, combine, reward, admin` |
| 5. 관계 및 참조 | 다른 데이터와의 FK/ID 참조 관계를 설명합니다. | `ElementRecipeData.result_element_id → ElementData.element_id` |
| 6. 데이터 목록 | 실제 데이터 표를 넣거나 원본 CSV/Sheet를 링크합니다. | `FIRE / 불꽃 / #E34A33` |
| 7. 검증 규칙 | 저장·입력 시 지켜야 할 데이터 유효성 규칙을 적습니다. | `element_name은 중복 불가`, `color_hex는 HEX 형식` |
| 8. 변경/마이그레이션 규칙 | 필드 변경, ID 폐기, 호환성 처리 방식을 적습니다. | `사용 중인 ID는 삭제하지 않고 status=inactive 처리` |
| 9. Deprecated 데이터 | 더 이상 신규 사용하지 않는 필드/테이블과 대체 대상을 기록합니다. | `UserElementStorageData: deprecated, 대체 규칙은 제작 팔레트 제한` |
| 10. 미확정 항목 | 스키마나 값 중 아직 결정되지 않은 부분을 적습니다. | `ELEMENT_DESC_MAX_LENGTH TBD` |
| 변경 이력 | 스키마·enum·제약 변경을 기록합니다. | `v0.2.0: secondary_color_hex 추가` |

## 스키마 표 예시

```md
| 필드 | 타입 | 필수 | 제약 | 설명 |
|---|---|---|---|---|
| element_id | UUID | Y | PK, UNIQUE | 원소 고유 ID |
| element_name | STRING | Y | UNIQUE | 표시 이름 |
| status | ENUM | Y | active/review/inactive | 사용 상태 |
```

## 데이터 목록 예시

```md
| ID | 이름 | 분류 | 상태 |
|---|---|---|---|
| FIRE | 불꽃 | 기본 원소 | active |
| STEEL | 강철 | 기본 원소 | active |
```

## Data 문서 작성 원칙

- 실제 값과 예시 값을 명확히 구분합니다.
- 미확정 기본값을 임의로 채우지 않고 `TBD`로 둡니다.
- 사용 중인 ID나 필드는 가능하면 삭제보다 Deprecated/Inactive 처리합니다.
- 대량 데이터의 실제 원본이 Google Sheets/CSV라면 문서에 복제하지 않고 `source`와 링크를 남길 수 있습니다.
- 데이터 규칙이 게임 플레이 정책을 바꾼다면 Data 문서에서 독자적으로 결정하지 않고 시스템 기획서 또는 Decision을 먼저 수정합니다.
