# 문서 수명주기와 Agent 규칙

## 문서 수명주기

`draft → review → approved → deprecated`

### draft

자유롭게 수정할 수 있는 작업 문서다. 미확정 항목을 포함할 수 있다.

### review

검토 중인 문서다. 구조 변경이나 정책 변경은 변경 이유를 남긴다.

### approved

현재 프로젝트의 기준 문서다. Agent는 사용자의 명시적 지시 없이 핵심 정책을 바꾸지 않는다.

### deprecated

더 이상 신규 구현의 기준으로 사용하지 않는 문서다. 기록 보존을 위해 원칙적으로 삭제하지 않는다.

## Deprecated 정책

1. 신규 문서가 있다면 신규 문서를 먼저 작성한다.
2. 신규 문서의 `supersedes`에 이전 문서를 연결한다.
3. 이전 문서의 `status`를 `deprecated`로 변경한다.
4. 이전 문서의 `deprecated`를 `true`로 변경한다.
5. 이전 문서의 `superseded_by`에 신규 문서를 연결한다.
6. 이전 문서 상단에 대체 문서를 안내한다.

문서는 중복, 오래됨, 구조 개편만을 이유로 바로 삭제하지 않는다. 개인정보, 비밀정보 노출, 완전히 잘못 생성된 파일처럼 보존 가치보다 위험이 큰 경우에만 삭제를 고려한다.

## Agent 강제 규칙

### 문서 생성

- 새 기획 문서는 반드시 Front Matter 규격을 포함한다.
- 가장 구체적인 `doc_type`을 선택한다.
- 기존 문서와 책임이 중복되면 새 문서를 만들기 전에 기존 문서 확장 또는 대체 여부를 판단한다.
- 확인할 수 없는 사실, 수치, 일정, 담당자를 생성하지 않는다.

### 문서 수정

- 수정 전 `status`, `doc_type`, `scope`, `related`를 확인한다.
- `approved` 문서의 핵심 결정은 사용자 지시 또는 명시적인 새 결정 근거 없이는 바꾸지 않는다.
- 시스템 간 충돌이 발견되면 한쪽을 임의로 선택하지 않고 `decision` 문서에 기록한다.
- 의미가 바뀌면 `updated`와 필요 시 `version`을 갱신한다.
- 단순 문장 정리로 의미가 바뀌지 않으면 버전을 올리지 않아도 된다.

### 문서 삭제

- 기본 동작은 삭제가 아니라 Deprecated 처리다.
- 다른 문서에서 참조 중인 문서는 즉시 삭제하지 않는다.
- 대체 문서가 존재하면 양방향 대체 관계를 남긴다.

### 출처와 충돌

- Google Docs/Sheets에서 마이그레이션한 내용은 `source`를 남길 수 있다.
- 여러 원본이 충돌하면 최신 수정일만으로 자동 승자를 정하지 않는다.
- 구현 상태와 기획 정책이 충돌하면 둘을 별도 정보로 유지한다.
- 실제 코드 구현이 기획과 다르다는 이유만으로 기획 문서를 자동 수정하지 않는다.

### 문서 분리 기준

- 게임 전체 목표와 제품 관점은 PRD.
- 플레이 경험과 전체 게임 구조는 GDD.
- 특정 시스템의 규칙과 상호작용은 시스템 기획서.
- 데이터로 제작·운영되는 게임 내용은 콘텐츠 기획서.
- 구현 단위의 입출력·예외·상태는 기능정의서.
- 일정, 작업, 담당, 의존성은 WBS.
- 시스템 간 충돌 또는 의사결정 로그는 Decision 문서.
