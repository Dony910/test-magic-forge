# Plane 활용 가이드

<Info>
  **Mintlify는 기획과 정책의 원본**, **Plane은 실행 업무의 현재 상태**, **GitHub는 코드 변경의 근거**로 사용합니다. 같은 정보를 여러 곳에 복제하기보다 각 도구가 책임지는 정보를 명확히 나눕니다.
</Info>

- Plane 프로젝트: [마법공방의 대장장이](https://plane.dony910.xyz/hgm-games/projects/1d33cafb-9df2-458f-b676-511691643701/issues)
- 상위 작업 구조: [WBS](/project/wbs)
- 문서 작성 기준: [문서 작성 공통 규칙](/standards/document-rules)
- 문서 변경 기준: [문서 수명주기와 Agent 규칙](/standards/lifecycle-agent-rules)

<Warning>
  이 문서의 Plane 상태와 템플릿 구성은 **2026-09-08** 기준입니다. Plane의 워크플로우나 템플릿을 바꾸면 이 가이드도 함께 수정합니다.
</Warning>

## 1. 도구별 책임

| 도구 | 관리하는 정보 | 관리하지 않는 정보 |
| --- | --- | --- |
| **Mintlify** | PRD, GDD, 시스템 규칙, 기능정의, 콘텐츠 정의, 결정 기록 | 개인별 실시간 작업 상태 |
| **Plane** | 태스크, 담당자, 상태, 기한, 블로커, 후속 작업 | 시스템 규칙의 원본 전문 |
| **GitHub** | 코드, 브랜치, PR, 커밋, 구현 리뷰 | 기획 정책의 원본 |

Plane 태스크에 필요한 기획 내용을 전부 복사하지 않습니다. 태스크에는 **실행에 필요한 요약과 완료 조건**을 적고, 상세 규칙은 Mintlify 문서를 연결합니다.

## 2. 현재 워크플로우

현재 프로젝트는 다음 6개 상태를 사용합니다.

| 상태 | 사용 기준 |
| --- | --- |
| `Backlog` | 해야 할 가능성은 있지만 일정, 범위, 착수 조건이 아직 확정되지 않은 작업 |
| `시작하지 않음` | 목적, 범위, 완료 조건이 정리되어 바로 시작할 수 있는 작업 |
| `대기 중` | 선행 작업, 의사결정, 에셋, 리뷰 등 외부 조건 때문에 현재 진행할 수 없는 작업 |
| `진행 중` | 담당자가 실제 작업을 시작한 상태 |
| `완료` | 완료 조건을 충족하고 필요한 검증까지 끝난 상태 |
| `연기됨` | 현재 범위에서는 수행하지 않기로 결정했지만 기록은 남겨야 하는 작업 |

### 상태 전환 기준

- `Backlog → 시작하지 않음`: 목적, 작업 범위, 완료 조건이 작성되어 있습니다.
- `시작하지 않음 → 진행 중`: 담당자가 실제 작업을 시작합니다.
- `진행 중 → 대기 중`: 본인 작업만으로 해결할 수 없는 명확한 블로커가 생깁니다.
- `대기 중 → 진행 중`: 블로커가 해소되어 작업을 재개합니다.
- `진행 중 → 완료`: 완료 조건과 검증 기준을 모두 확인했습니다.
- `어떤 상태 → 연기됨`: PO 또는 담당자 합의로 현재 개발 범위에서 제외합니다.

<Note>
  현재 Plane에는 별도의 `리뷰 중` 상태가 없습니다. 리뷰는 태스크의 **검증 과정 또는 완료 조건**으로 처리합니다. 단순히 작업을 잠시 멈춘 경우도 `연기됨`이 아니라, 재개 조건이 명확하다면 `대기 중`을 사용합니다.
</Note>

## 3. 태스크 제목 규칙

제목은 작업 행위보다 **완료 결과**가 드러나게 작성합니다.

```text
[분야] 대상 - 완료 결과
```

예시:

```text
[개발] 원소 조합 - 조합 결과 생성 로직 구현
[기획] 무기 태그 - 태그 부여 규칙 확정
[아트] 단검 파츠 - 기본 실루엣 3종 제작
[버그] 원소 조합 결과가 사라짐 - 조합 직후 저장 시
```

피해야 하는 제목:

```text
원소 시스템 작업
무기 기획
UI 수정
버그 고치기
```

제목만 보고 결과를 예상할 수 없다면 범위가 너무 크거나 모호한 태스크일 가능성이 높습니다.

## 4. 모든 태스크에 필요한 항목

좋은 태스크는 담당자가 아닌 팀원이 읽어도 다음 세 질문에 답할 수 있어야 합니다.

1. **왜 하는가?**
2. **어디까지 하는가?**
3. **무엇이 되면 끝인가?**

### 목적 / 배경

이 작업이 필요한 이유와 해결하려는 문제를 1~3문장으로 작성합니다.

### 작업 범위

- **포함:** 이번 태스크에서 반드시 처리할 범위
- **제외:** 관련은 있지만 이번 태스크에서는 처리하지 않을 범위

범위가 계속 늘어나면 기존 태스크를 키우기보다 후속 태스크로 분리합니다.

### 완료 조건

완료 조건은 작업 목록이 아니라 **결과를 판정하는 기준**입니다.

좋은 예:

- 조합 가능한 두 원소를 입력하면 정의된 결과 원소가 생성됩니다.
- 잘못된 조합 입력은 실패 결과를 반환하고 데이터가 변경되지 않습니다.
- 관련 시스템 기획서와 구현 결과가 일치합니다.

나쁜 예:

- 조합 코드 작성
- 테스트하기
- 문서 보기

### 검증 방법

어떤 빌드, 화면, 테스트, 리뷰로 완료 여부를 확인할지 적습니다.

### 산출물 / 연결

작업 유형에 맞게 다음을 연결합니다.

- Mintlify 기획 문서
- GitHub 브랜치 / PR / 커밋
- 빌드 / 플레이 영상
- 원본 아트 파일 / Export 경로
- 로그 / 스크린샷 / 레퍼런스

### 의존성 / 블로커

선행 작업, 필요한 결정, 다른 팀의 산출물을 적습니다. 없으면 `없음`이라고 명시합니다.

## 5. 태스크 템플릿 사용법

현재 프로젝트에는 `템플릿` 라벨이 붙은 다음 네 개의 공용 Work Item이 있습니다.

- `[TEMPLATE] 기획 태스크` (`SMTTM-12`)
- `[TEMPLATE] 개발 태스크` (`SMTTM-11`)
- `[TEMPLATE] 아트 태스크` (`SMTTM-13`)
- `[TEMPLATE] 버그 태스크` (`SMTTM-14`)

네 템플릿은 모두 `Backlog`에 보관합니다. 실제 작업으로 이동시키지 않습니다.

### 새 태스크를 만드는 절차

1. `템플릿` 라벨로 가장 가까운 템플릿을 찾습니다.
2. 해당 Work Item을 복제합니다.
3. 제목의 `[TEMPLATE]`를 실제 제목으로 교체합니다.
4. 복제한 실제 태스크에서는 `템플릿` 라벨을 제거합니다.
5. 담당자, 상태, 필요하면 기한과 우선순위를 설정합니다.
6. 본문의 안내 문구와 빈 항목을 실제 작업 내용으로 교체합니다.
7. 관련 Mintlify 문서와 GitHub PR 등 근거를 연결합니다.

<Warning>
  템플릿 원본 자체를 실제 작업으로 사용하거나 완료 처리하지 않습니다. 템플릿 내용을 개선하려면 원본 Work Item을 수정하고, 운영 규칙이 달라졌다면 이 문서도 함께 수정합니다.
</Warning>

## 6. 템플릿별 기준

### 기획 태스크

사용 시점:

- 새로운 시스템 규칙 정의
- 기존 정책 수정
- 개발·아트가 작업하기 전에 결정이 필요한 항목

주요 항목:

- 관련 PRD / GDD / 시스템 문서
- 기획 범위와 제외 범위
- 결정해야 할 정책과 예외 규칙
- 정상·경계·예외 시나리오 검증
- 개발·아트가 추가 해석 없이 시작할 수 있는지 여부

기획 태스크의 완료는 **문서를 작성했는가**가 아니라 **다른 직군이 그 문서로 작업을 시작할 수 있는가**로 판단합니다.

### 개발 태스크

사용 시점:

- 기능 구현
- 리팩터링
- 데이터 연동
- 시스템 통합

주요 항목:

- 구현 범위와 제외 범위
- 구현 요구사항
- 정상 / 실패 / 예외 케이스
- 테스트 환경과 확인 절차
- 기획 문서와 PR 연결

완료 전에는 필요한 로그나 임시 디버그 코드가 정리되었는지도 확인합니다.

### 아트 태스크

사용 시점:

- 콘셉트, UI, 2D/3D 에셋 제작
- 파츠 및 베리에이션 제작
- 인게임 적용을 위한 리소스 작업

주요 항목:

- 사용 위치와 목적
- 레퍼런스와 스타일 기준
- 수량, 규격, 해상도, 비율
- 파일 형식과 원본 / Export 경로
- 실제 게임 화면에서의 가독성 검증

게임에서 사용하는 에셋은 원본 파일 제작만으로 완료하지 않습니다. 실제 적용 환경에서 결과를 확인합니다.

### 버그 태스크

사용 시점:

- 기존 동작이 기대 결과와 다른 경우
- 크래시, 데이터 유실, 잘못된 UI 또는 게임플레이 동작

주요 항목:

- 발생 환경
- 재현 절차
- 기대 결과 / 실제 결과
- 영향 범위와 발생 빈도
- 원인과 수정 내용
- 수정 후 회귀 검증

버그는 다른 사람이 그대로 따라 할 수 있는 **재현 절차**를 남기는 것을 원칙으로 합니다. 재현되지 않는다면 확인한 환경과 시도한 조건을 기록합니다.

## 7. 태스크 크기와 분리 기준

한 태스크에는 하나의 명확한 결과를 둡니다.

다음 상황이면 분리를 검토합니다.

- 담당자가 둘 이상이고 서로 독립적으로 완료할 수 있습니다.
- 완료 조건이 서로 다른 결과를 요구합니다.
- 기획 확정과 구현이 한 태스크에 섞여 있습니다.
- 개발과 아트 작업이 한 태스크에 함께 들어 있습니다.
- 일부만 완료해도 독립적인 가치가 있습니다.

예를 들어 `원소 시스템 구현` 하나로 만들기보다 다음처럼 나눕니다.

```text
[기획] 원소 조합 - 조합 규칙 확정
[개발] 원소 데이터 - 데이터 구조 구현
[개발] 원소 조합 - 조합 결과 판정 구현
[개발] 원소 조합 UI - 조합 결과 표시 연동
```

## 8. 의존성 관리

작업 순서가 중요한 경우 단순히 본문에 적는 것에서 끝내지 말고 Plane의 Work Item 관계를 사용합니다.

예시:

```text
[기획] 원소 조합 - 조합 규칙 확정
        ↓ blocks
[개발] 원소 조합 - 조합 결과 판정 구현
        ↓ blocks
[개발] 원소 조합 UI - 조합 결과 표시 연동
```

선행 태스크가 끝나지 않아 진행할 수 없다면 후속 태스크를 `대기 중`으로 두고, 무엇을 기다리는지 본문에 명시합니다.

## 9. Mintlify와 Plane 연결 규칙

기획의 원본은 Mintlify에 유지합니다.

- Mintlify 문서가 수정되어 구현 작업이 필요하면 Plane 태스크를 생성합니다.
- Plane에서 정책이 새로 확정되었다면 관련 Mintlify 문서를 수정합니다.
- 태스크 본문에 관련 Mintlify 문서를 연결합니다.
- 구현 중 기획과 다른 결정을 했다면 코드만 맞추지 말고 문서도 갱신합니다.
- 중요한 정책 변경은 필요하면 [Decision Log](/project/decisions)에 남깁니다.

즉, **Plane의 완료 상태와 Mintlify 문서의 현재 정의가 서로 어긋나지 않도록 관리**합니다.

## 10. WBS와 Plane의 관계

[WBS](/project/wbs)는 프로젝트의 **상위 작업 구조와 주요 의존성**을 보여주는 문서입니다. Plane은 그 구조에서 파생된 **실제 실행 태스크의 현재 상태**를 관리합니다.

<Note>
  WBS의 상태 표기와 Plane 워크플로우를 1:1로 맞출 필요는 없습니다. WBS는 상위 범위와 계획을 설명하고, 일상적인 진행 상태는 Plane을 기준으로 확인합니다.
</Note>

WBS의 작업 하나가 실제로는 여러 Plane 태스크로 분해될 수 있습니다. 반대로 Plane의 작은 버그나 후속 수정까지 WBS에 모두 추가할 필요는 없습니다.

## 11. 우선순위와 기한 권장 기준

현재 프로젝트에서는 모든 태스크에 우선순위와 기한을 강제하지 않습니다.

- **기한:** 외부 일정, 마일스톤, 다른 작업의 착수일에 영향을 주는 경우 설정합니다.
- **우선순위:** 기본은 `none`으로 두고, 작업 순서 판단에 실제로 필요한 경우에만 설정합니다.
- **긴급도와 중요도 구분:** 단순히 빨리 하고 싶다는 이유로 `urgent`를 사용하지 않습니다.

기한이 지난 태스크가 생기면 날짜만 뒤로 미루지 말고 범위, 블로커, 우선순위를 먼저 확인합니다.

## 12. 완료 처리 체크리스트

태스크를 `완료`로 옮기기 전에 확인합니다.

- [ ] 태스크의 완료 조건을 모두 충족했습니다.
- [ ] 필요한 검증을 실제로 수행했습니다.
- [ ] 관련 Mintlify 문서가 현재 결과와 일치합니다.
- [ ] 코드, PR, 빌드, 에셋 등 필요한 산출물을 연결했습니다.
- [ ] 작업 중 변경된 결정과 범위를 기록했습니다.
- [ ] 남은 작업이 있다면 별도의 후속 태스크로 분리했습니다.

## 13. 운영 원칙 요약

- 기획과 정책의 원본은 Mintlify에 둡니다.
- 실행 단위는 Plane 태스크로 만듭니다.
- 태스크에는 반드시 완료 결과를 적습니다.
- `대기 중`과 `연기됨`을 구분합니다.
- 템플릿은 복제해서 사용하고 원본은 `Backlog`에 유지합니다.
- 완료 상태는 검증이 끝난 뒤에만 사용합니다.
- 작업 중 생긴 중요한 결정은 관련 문서로 되돌려 반영합니다.

<Info>
  Plane의 목적은 작업을 많이 등록하는 것이 아니라, **지금 무엇이 결정되어 있고, 누가 무엇을 하고 있으며, 무엇이 끝났는지**를 팀 전체가 같은 기준으로 알 수 있게 만드는 것입니다.
</Info>
